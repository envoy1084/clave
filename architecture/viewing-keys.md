# Threshold viewing keys

## Purpose

`clave-crypto` (`crates/crypto`) implements every viewing-key operation of a vault. The vault's incoming viewing secret
`ivsk` is generated by distributed key generation and never assembled: each member's keeper holds a share, the PXE
obtains `address_secret · P` through threshold ECDH with proofs, and shares move to a new committee by resharing while
the vault keeps its address. All threshold code lives in this crate.

## Aztec compatibility

Verified byte for byte against `@aztec-labs/*` 6.0.0 by golden vectors (`crates/crypto/tests/vectors/aztec.json`,
generated and checked by `tools/aztec-vectors`; run it on every Aztec upgrade):

| Item              | Rule                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------- |
| Curve             | Grumpkin `y^2 = x^3 - 17`; generator `(1, sqrt(-16))`; scalars mod BN254 `Fq`, coordinates mod BN254 `Fr` |
| Point encoding    | `x ‖ y`, 32-byte big-endian each; compressed: `x` with the top bit set when `y ≤ (p - 1) / 2`             |
| Poseidon2         | `t = 4` permutation; sponge rate 3, capacity initialised to `len · 2^64`; separator prepended as a field  |
| Preaddress        | `Poseidon2([public_keys_hash, partial_address], 993442748)` (`CONTRACT_ADDRESS_V3`)                       |
| Address           | `x` of `preaddress · G + Ivpk`                                                                            |
| Address secret    | `σ · (ivsk + preaddress)`, `σ = -1` when `preaddress · G + Ivpk` has `y > (p - 1) / 2`, else `+1`         |
| App-siloed secret | `Poseidon2([S.x, S.y, app], 1707851664)` (`APP_SILOED_ECDH_SHARED_SECRET`) for the raw ECDH point `S`     |

The sign `σ` depends only on public data, so every member applies it to its share without learning `ivsk`.

## Key model

| Value                              | Held by             | Notes                                                                      |
| ---------------------------------- | ------------------- | -------------------------------------------------------------------------- |
| Viewing share `s_i`                | Member `i`'s keeper | Never backed up or exported; replaced on every reshare                     |
| Group key `Ivpk`                   | Public              | Constant term of the shared polynomial; part of the vault address          |
| Verification share `Y_i = s_i · G` | Public              | Committed on chain via `committee_commitment` ([contract.md](contract.md)) |
| Address verification share `A_i`   | Public              | `σ · (Y_i + preaddress · G)`; DLEQ proofs are checked against it           |
| Transport key                      | Each keeper         | X25519, for envelopes                                                      |

Member indices are `1..=n` and equal the member's signer slot plus one.

## Distributed key generation

Feldman DKG with Schnorr proofs of knowledge (FROST `KeyGen` shape), as a transport-agnostic state machine (`dkg`):

1. **Round 1 (broadcast).** Each member `j` samples `f_j` of degree `t - 1`, publishes commitments
   `C_{j,k} = a_{j,k} · G` and a proof of knowledge `(R, μ)` of `a_{j,0}`, with challenge
   `SHA-512("clave.dkg.pok.v0" ‖ session ‖ be32(j) ‖ C_{j,0} ‖ R)` read little-endian and reduced mod `q`.
2. **Round 2 (private).** After verifying every proof, `j` sends `f_j(i)` to each `i`, sealed in an envelope (kind 1)
   and signed at the wire layer.
3. **Finalize.** `i` checks each `f_j(i)` against `C_j` (failure names dealer `j`: `InvalidShare`), sets
   `s_i = Σ_j f_j(i)` and `Ivpk = Σ_j C_{j,0}`, and records a transcript hash every member must confirm:
   `SHA-512("clave.dkg.transcript.v0" ‖ session ‖ be64(t) ‖ for each participant: be32(j) ‖ C_j points)`.

A revealed share that does not match the dealer's commitments (`complaint_is_valid`) proves the dealer misbehaved,
given the dealer's signature on the envelope. A revealed share that does match is unattributable, so the keeper aborts
without blame ([keeper.md](keeper.md#ceremonies)).

Manifests carry only verification shares. `Commitments::interpolate` rebuilds the committee's Feldman commitments from
them (rejecting shares that do not lie on one polynomial), which resharing needs, and `KeyShare::restore` rebuilds a
stored share after checking it against them.

The DKG is custom rather than `frost-core`'s: `frost-core` multiplies secret coefficients through its group type (so a
constant-time point type would be needed anyway), its refresh cannot move shares to a different committee, and its
audit does not cover a Grumpkin ciphersuite. DKG and resharing share one Feldman and Lagrange core (`shamir`).

## Threshold ECDH

For a vault with context `(preaddress h, sign σ)` (`ecdh`, `aztec::AddressContext`):

```text
member i:  x_i = σ · (s_i + h)            A_i = x_i · G = σ · (Y_i + h · G)   (public)
request:   input point P (note ephemeral key, handshake key, or counterparty address point)
partial:   D_i = x_i · P
proof:     Chaum-Pedersen DLEQ that log_G(A_i) = log_P(D_i)
combine:   address_secret · P = Σ_{i∈S} λ_i^S · D_i   for any |S| = t_v
```

- Lagrange coefficients over any qualified set sum to one, so shifting every share by `h` and applying `σ` yields shares
  of the address secret.
- DLEQ challenge: `SHA-512("clave.dleq.v0" ‖ vault ‖ be32(epoch) ‖ be32(i) ‖ G ‖ A_i ‖ P ‖ D_i ‖ R_G ‖ R_P)` read
  little-endian and reduced mod `q`; the proof is `(c, z = k + c · x_i)`. It binds the partial to the vault, the epoch,
  the member and the input point, so it cannot be replayed or relabelled.
- `verify_and_combine` drops invalid partials, reports their members, and combines the first `t_v` valid ones.

The PXE side (which oracle calls reach this, batching, caching) is in [pxe-integration.md](pxe-integration.md); the
network side (who is asked, budgets, audit) is in [keeper.md](keeper.md#threshold-ecdh).

## Resharing

Same secret, fresh polynomial, new committee and threshold (`reshare`):

1. A qualified set `S` of exactly `t_v` current members deals. Dealer `i` shares `λ_i^S · s_i` with a polynomial of the
   new threshold `t_v'` and publishes its commitments.
2. Every receiver checks each dealer's constant term equals `λ_i^S · Y_i` (`InvalidProof` otherwise), so a dealer can
   only contribute its real share.
3. New member `j` verifies its sub-shares (sealed as envelope kind 2; `InvalidShare` names the dealer), sets
   `s'_j = Σ_{i∈S} g_i(j)`, and checks the new constant terms sum to the unchanged `Ivpk` (`GroupKeyMismatch`
   otherwise).
4. Transcript: `SHA-512("clave.reshare.transcript.v0" ‖ session ‖ be64(t_v') ‖ be32(new indices) ‖ for each dealer:
   be32(i) ‖ commitment points)`.

Old and new shares lie on different polynomials and never combine. The new verification shares give the
`committee_commitment` that `rotate_membership` stores on chain. The membership flow around this is in
[membership.md](membership.md).

## Envelopes

HPKE (RFC 9180) Auth mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, ChaCha20-Poly1305 (`envelope`). The HPKE `info` is

```text
"clave.envelope.v0" ‖ session (32) ‖ be32(epoch) ‖ be16(kind) ‖ be32(sender) ‖ be32(recipient)
```

so an envelope opens only for its ceremony, epoch, message kind and member pair. HPKE authenticates the sender to the
recipient only; third-party attribution for complaints comes from the sender's signature at the wire layer.

| Kind | Carries                                        | Session            | Epoch     | Sender / recipient        |
| ---: | ---------------------------------------------- | ------------------ | --------- | ------------------------- |
|    1 | DKG round 2 share                              | DKG session        | 0         | dealer / member index     |
|    2 | Reshare sub-share                              | reshare session    | old epoch | dealer / new member index |
|    3 | Relay mailbox payload (`mailbox`)              | mailbox id         | UTC day   | 0 / 0                     |
|    4 | Lobby protocol secrets (`lobby::seal_secrets`) | lobby plan session | 0         | 1 (host) / member index   |

## Lobby helpers

`lobby::join_proof = HMAC-SHA256(invite secret, "clave.lobby.join.v0" ‖ lobby id ‖ joiner identity ‖ joiner transport)`,
verified with a constant-time comparison. `seal_secrets` / `open_secrets` carry the engine's opaque protocol secrets
from a lobby's host to each member as envelope kind 4 ([keeper.md](keeper.md#lobbies)).

## Side-channel posture

- Secret scalars (`SecretScalar`) are zeroized on drop, compared with `subtle`, and have a redacted `Debug`.
- Every multiplication by a secret (shares, coefficients, nonces) uses `ct::mul`: homogeneous projective coordinates
  with the complete `a = 0` addition formula (Renes-Costello-Batina 2016, Algorithm 7), a fixed 4-bit window over all
  256 bits with a constant-time table scan, and Fermat inversion with a fixed exponent. It matches arkworks for edge and
  random scalars (unit and property tests).
- Public scalars (verification, Lagrange combination) use arkworks' variable-time multiplication.
- Known residual: arkworks' Montgomery multiplication has a conditional final subtraction. It is unreviewed.

## Guarantees and limits

| Property                                                   | Holds when                                              |
| ---------------------------------------------------------- | ------------------------------------------------------- |
| No party learns `ivsk`                                     | Fewer than `t_v` members collude                        |
| A cheating member cannot corrupt a decryption undetected   | Always (DLEQ on every partial)                          |
| A removed member cannot decrypt anything after the reshare | Fewer than `t_v` removed per reshare; old shares erased |
| The vault address survives membership changes              | Always (`Ivpk` unchanged)                               |
| Data seen before removal                                   | Never revocable                                         |
